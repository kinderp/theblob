# ADR-0034: Root publisher derives prepared activation requests from admitted materializations

## Status

Accepted for validation in a disposable NixOS VM. Physical-node execution remains disabled.

## Context

ADR-0033 replaced an in-code prepared activation fixture with a strict root-owned request store and proved crash-safe `ready -> inflight -> completed/failed` handling. The production-shaped executor accepts only an opaque request id and never accepts a closure, executable or argv from the D-Bus caller.

One gap remained immediately upstream: ADR-0033 still used a test fixture to create the complete prepared request file. A production control-plane process must not be allowed to write those files directly because doing so would let it choose privileged execution fields and forge readiness evidence.

## Decision

Add a distinct root request publisher. The caller may request preparation using only:

- the id of an already admitted materialization;
- one bounded action: `preview` or temporary `test`.

The publisher obtains every security-sensitive field from trusted local sources:

- node, candidate, SystemSpec, materialization operation and immutable closure come from a root-owned materialization-admission record;
- current architecture, substrate, power observation, free space, boot generation and rollback reference come from the root process running the read-only NixOS probe;
- enrollment, trust, storage-health and local-console confirmations come from root-owned daemon policy/configuration;
- effect class, required authority, exact `switch-to-configuration` program and its single argument are derived by the immutable NixOS activation planner;
- authorization id is generated by root from `/dev/urandom`;
- preparation/expiry timestamps are generated by root from the observed readiness snapshot.

The publisher performs a real polkit check for the live system-D-Bus sender against that fully derived request. Only after a successful grant does it create the canonical root-owned mode-0600 request in the `ready` directory.

Execution remains a separate operation and requires a second real polkit check before the crash-safe claim, permit issuance and privileged root boundary. The two checks intentionally separate "prepare this exact privileged request" from "execute this exact prepared request" while this safety pilot is being validated.

## Materialization admission

A materialization admission is a separate root-owned mode-0600 canonical record containing:

- node;
- candidate;
- SystemSpec;
- materialization operation;
- immutable `/nix/store/...` closure;
- admission timestamp;
- provenance evidence.

The publisher rejects missing, symlinked, non-root-owned, permissively writable/readable, non-canonical or non-store admissions before polkit or request publication.

This ADR does **not** claim that creation of those admissions is solved. The KVM checkpoint stages them with a test-only root fixture. The next checkpoint must prove how an actual successful non-privileged materialization becomes an admitted root record without allowing the control plane to substitute an arbitrary closure.

## Required proof

The disposable KVM test must prove:

1. an unprivileged caller cannot read or write the materialization admission record;
2. an unknown admission id cannot publish a request;
3. a root admission with invalid permissions is rejected;
4. live `test` preparation is rejected when the root probe cannot establish the boot-default/rollback readiness preconditions;
5. after the real boot-default profile exists, authorized preview preparation publishes a root-generated authorization id and a mode-0600 request;
6. candidate, SystemSpec and closure in the prepared request come from the admission, not the caller;
7. execution of the published preview still traverses the independent polkit/claim/permit/root-boundary chain and leaves baseline live;
8. a caller denied by polkit cannot publish a live-test request;
9. a caller authorized for test can publish and then independently authorize execution of the exact admitted closure;
10. temporary activation leaves the boot-default baseline untouched and reboot restores baseline;
11. completed published requests remain non-replayable after reboot.

## Safety boundary

Still impossible through this path:

- persistent `switch`;
- persistent `boot`;
- mutable-source `nixos-rebuild`;
- caller-selected system closure;
- caller-selected executable or argv;
- caller-supplied readiness evidence;
- direct unprivileged writes to the prepared request inbox;
- physical-node execution.

## Next checkpoint

Prove materialization admission itself: bind a successful non-privileged materialization result to an immutable candidate/source/derivation identity and have root independently validate that the reported closure is exactly the output of that admitted materialization. Only after that provenance boundary and an explicit inflight-recovery workflow are green should physical-hardware enablement be reconsidered.
